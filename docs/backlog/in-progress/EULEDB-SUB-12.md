## Goal

The key hierarchy. A passphrase derives a key-encryption key via Argon2id, which wraps a separate,
rotatable AES-256-GCM data-encryption key persisted alongside the database. A wrong passphrase fails
closed with a distinct error and the data-encryption key stays unrecoverable.

## Scope, and what was cut away from it

AC-20 originally bundled this with encrypting the data itself. It was split, and AC-75 appended, because
the two are different sizes of problem — the reasoning is in the specification's § Decisions taken and
in ADR-002. **This ticket is the key hierarchy only. No byte of table data is encrypted by it.** The
data path is SUB-18, and rotation (SUB-13) now follows the data path rather than this ticket, because
"previously written data stays readable" is not observable while nothing is encrypted.

## Design

Envelope encryption, so that rotating the data-encryption key never rewrites payload:

```text
passphrase ──Argon2id(salt, params)──▶ KEK ──AES-256-GCM──▶ wrapped DEK ──▶ (data, SUB-18)
                     │                                             │
                     └── salt and params stored in the keyfile ─────┘
```

- **Argon2id**, not Argon2i or Argon2d: it is the variant the RFC recommends against both side-channel
  and GPU attackers, and it is the default for password hashing.
- **The salt and the Argon2 parameters are stored in the keyfile.** Not to keep them secret — they are
  not secrets — but because a KEK cannot be re-derived without them, and hardcoding parameters means a
  future increase locks every existing database out.
- **The DEK is generated by a CSPRNG and never derived from the passphrase.** That is what makes
  rotation possible: a new DEK is a new random key, and the old ciphertext stays readable under the old
  one during a migration.
- **Key material is zeroized on drop.** A key that lingers in freed memory is recoverable from a core
  dump or a swap file.
- **The wrong-passphrase failure is the GCM tag failing on unwrap**, which is exactly the fail-closed
  behaviour the criterion asks for — there is no separate check to get wrong, and no way to distinguish
  a wrong passphrase from a corrupted keyfile without leaking which one it was.

## Steps

1. `ZeroizingKey` newtype over a 32-byte array, zeroized on drop, with no `Debug` that prints it.
2. `KeyDerivation` carrying the salt and the Argon2 parameters, serialisable into the keyfile.
3. `Keyring::create(passphrase)` — generate a DEK, derive a KEK, wrap, return the keyring and the
   serialised keyfile bytes.
4. `Keyring::open(keyfile, passphrase)` — re-derive the KEK, unwrap, fail closed on a bad tag.
5. A distinct error type where a wrong passphrase, a malformed keyfile and an unsupported version are
   separate variants, because they need different responses from a caller.

## TDD record, and the four gaps the mutation check found

Seven tests written first, all RED on `no Keyring in the root`. Then the mutation pass, which is where
this ticket earned its keep — **four of five mutations were not caught by the tests that had just been
written**:

| Mutation | Caught first time | What was wrong, and the fix |
|---|---|---|
| the key prints itself in `Debug` | yes | — |
| **salt fixed instead of random** | **no** | the test compared whole keyfiles, which differ anyway because the nonce and wrapped key are random. It now slices the salt out of the keyfile and compares that |
| **nonce fixed instead of random** | **no** | not tested at all. Now sliced and compared. Not immediately catastrophic here, since each keyring has its own key — but a fixed nonce is a habit that becomes catastrophic the moment a key is reused, and the data path will reuse one |
| **keyfile length check removed** | **no** | a too-short keyfile was still caught further in, by the wrapped-key conversion, so the check looked redundant. A keyfile with *trailing* bytes now asserts the specific reason, which makes the check load-bearing |
| **format version bumped silently** | **no** | nothing pinned the layout. A test now asserts the keyfile length and the version byte, because both are a persisted contract: if they move, no database written by an earlier build opens |

The version and layout test is the one worth keeping in mind. It is not testing an implementation
detail — the keyfile is a format, and a format that changes without a version bump is a database that
stops opening.

## Out of scope / Guardrails

- **No table data is encrypted here** — SUB-18.
- **No rotation** — SUB-13, after the data path.
- **NEVER derive the DEK from the passphrase.** It would make rotation impossible without rewriting
  every byte, which is the whole point of the envelope.
- **NEVER print, log or `Debug`-format key material**, and never include it in an error.
- **Do not invent a key-derivation or wrapping scheme.** Argon2id and AES-256-GCM as the audited crates
  provide them, with parameters from their own guidance.
- No password *hashing* API. This derives a key, it does not store a verifier, and reaching for
  `PasswordHash` here would be the wrong tool.
